# Conservative stall observation

`prepare_dispatch.py --context-profile context-v1 --execution-profile bounded-native-v1 --stall-profile stall-v1` prepares an opt-in sandbox configuration. The default profile does not change. The existing worker image, SDK agent loop, confined gateway router, request limits and 300-second external allocation deadline remain in use.

The trusted host observes the original conversation every two seconds while the existing build/reconciliation call is active. It does not create another conversation, issue `/run`, restart a worker, or replenish reservations. The common `auto-common-v1` capability manifest permits only the existing explicit model, route, dummy worker key, usage identity and output-limit fields. Vendor-specific parameters and guessed model families are rejected before credential access.

Completed terminal/file/capture observations are paired to their original action IDs and reduced to action, error and diagnostic hashes. A native terminal soft timeout is not completed execution. Relevant workspace progress includes HEAD, semantic index state, tracked content and nonignored untracked content. Logs and obvious secret files are excluded. File reads refuse links and special files; scans and the private-config Git subprocess have byte, node, depth, output, CPU, memory and time bounds. An incomplete observation means unknown progress.

The default detector needs three equivalent completed failures, matching diagnostic evidence and workspace state, spanning at least four seconds. Six alternating A/B workspace observations with only repeated action/evidence signatures can identify oscillation. An unchanged workspace alone is never a stall. Successful read-only work, new diagnostic evidence and an in-flight long-running tool do not establish a failure loop.

Every unseen SDK observation is accounted for before a sampled failure is classified. If a burst includes different/new diagnostics or an unsupported observation, prior detection history is conservatively cleared. The latest result uses the current workspace observation; historical workspace hashes are not invented. Rapid bursts or edits wholly between polls can be missed. Workspace observation is bounded, not atomic, so this is a heuristic rather than an exhaustive progress proof.

On the first qualifying stall, the host checks that the original SDK loop is still running and saves and fsyncs a private intervention intent before sending one fixed diagnostic as a user message to the same conversation with `run=false`. No repository text or tool output is promoted into that message. The active agent may investigate differently or report a blocker. A terminal/stuck loop is never messaged or automatically resumed; SDK inactivity after delivery is contained and left for reconciliation. A terminal boundary can still race a read, so delivery is not assumed to imply consumption. A crash or uncertain delivery never causes a second send: the original allocation is contained instead. The journal lives beside the independent attempt anchor, outside the worker mount, and retains a bounded hashed observation cursor.

If a qualifying loop continues after the intervention, existing deadline cancellation stops the original worker and proxy and fences its unresolved attempt. Failure to complete fencing retains uncertainty. The result remains `unknown` with intervention/reconciliation status; it is not successful completion, rollback, a new allocation, a retry authorization, or a budget refund. Restart/reconciliation preserves the original identity and one-shot claim.

The sandbox and original allocation deadline remain the security boundary. Host/operator trust and worker-reported observation limitations still apply. Offline regressions precede any canary; a live SDK message-consumption canary and broader held-out evaluation are separate gates.

The [October 31 qualification report](../../docs/verification/harness-stall-2026-10-31/report.md) records offline coverage, both immutable canary candidates and final gateway reconciliation. The profile remains opt-in.
